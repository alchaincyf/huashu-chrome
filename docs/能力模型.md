# 能力模型：怎样才算「适配几乎所有网站」

这份文档回答一个问题：**面对一个没见过的网站，agent 该按什么顺序出牌。**

它不是设想出来的，是 2026-08-25 用小红书创作后台和 B 站创作中心两个真实站点
一路撞出来的。每条规则后面都跟着撞它的那堵墙。

---

## 一、三层模型

网页只有三种信息载体，没有第四种。能力就按这三种分，分完就不会再有
「又冒出一类网站搞不定」的情况。

| 层 | 载体 | 工具 | 什么时候用 |
|---|---|---|---|
| **操作层** | DOM | `snapshot` `click` `type` `select` `navigate` `scroll` | 要**做事**：填表、点按钮、走流程 |
| **数据层** | 网络 | `network` `fetch` | 要**拿数据**：列表、表格、统计 |
| **兜底层** | 像素 | `screenshot` | 前两层都失效：canvas 应用、图形界面 |

**最容易犯的错是拿操作层去干数据层的活。** 在 DOM 里刨数据，会掉进
下面第二节那个坑里。

---

## 二、拿数据：先看网络，别急着解析 DOM

### 撞墙实录

小红书笔记管理页，DOM 里每条笔记的数据长这样：

```
一个半小时，我开发上架两款iOS app  2024-11-05 13:22  165.97万3496878363079912491
```

五个数字糊成一串。就算用 `query` 按 `:nth-child` 拆开，也只能猜语义。
我按常识猜的顺序是「观看、点赞、收藏、评论、分享」——

而接口返回的是：

```json
{"view_count":1659680, "comments_count":3496, "likes":87836,
 "collected_count":30799, "shared_count":12491}
```

真实顺序是「观看、**评论**、**点赞**、**收藏**、分享」。**按常识猜必错**，
而且错得悄无声息——三个指标全串位，报告照样能写出来。

### 规则

1. **要数据先 `network`**，看这个页面调了哪些接口。字段名是站方自己写的，
   语义不用猜；数字是原始值，不是「165.97万」这种丢精度的展示格式。
2. `read_text` 和 `query` 是退路，不是首选。它们适合读文章正文，
   不适合读数据表。
3. 页面刚打开没记录，加 `reload:true` —— hook 走 `document_start` 注入，
   刷一次就能抓到首屏那批 XHR。

## 三、翻页：三条路，按顺序试

拿到接口地址后，怎么把整份数据取回来。

### 路线 A：直接 `fetch` 改参数（最快，先试这个）

```
fetch("https://member.bilibili.com/x/web/archives?pn=1&ps=100")
```

B 站这条路直接通——接口只认 cookie，`fetch` 在页面上下文里自动带。
19 次调用拿完 186 个稿件。

**陷阱：服务端可能悄悄忽略你的参数。** 我传 `ps=100`，响应里
`page:{"ps":10,"count":186}` ——它按 10 条返回，一声不吭。
**永远看响应里的分页字段，别信自己传的值。**

### 路线 B：UI 驱动 + 网络读取（最普适）

小红书这条路走不通：任何自造请求一律 `406`，签名是网关级的，
`x-s`/`x-t` 由页面 JS 生成，逆向不划算也不稳。

正解是**不跟签名斗**：

```
点「第 2 页」 → 页面自己发带签名的请求 → network 读响应
```

签名、token、风控、cookie 刷新全部由页面负责，agent 只管点和读。
**这个模式对所有网站都成立**，是路线 A 不通时的标准退路。

### 路线 C：换数据入口

小红书「笔记管理」页滚到底也不加载第二页（列表本身有问题）。
换到「数据看板 → 内容分析」，那里不但有正常分页，指标还更全
（多了曝光、封面点击率、涨粉、人均观看时长）。

**同一份数据，站内常有多个入口，接口干净程度差很多。**
在一个入口上死磕之前，先花一次调用看看有没有更好的门。

## 四、CSP：`eval` 是死路，参数化是活路

> **2026-08-26 订正**：这一节原来的判断是错的，而且错得很有代表性。
>
> 原文说「content script 里的 `new Function()` 受**页面**的 CSP 约束」。
> 实际上它受的是**扩展自己的** CSP——MV3 的 content script 跑在隔离世界里，
> 继承扩展的策略，而扩展 CSP 一律禁 `unsafe-eval`。
>
> 怎么发现的：在一个**自己写的、完全没有设 CSP 的本地页面**上，`eval` 照样被拦。
> 报错里那句 `script-src 'self' … chrome-extension://<uuid>` 末尾的来源才是真相，
> 当初只看了前半句就下了结论。
>
> 结论的方向因此完全变了：**原来的实现不是「大站上失效」，是「哪儿都不能用」**——
> 一个连本地空白页都跑不通的工具，等于不存在，却在工具表里占了一年的位置。
>
> 已改为走 `chrome.scripting.executeScript({world:'MAIN'})`。MAIN world 里受的
> 才是页面的 CSP，于是没设 CSP 的站点能用了，大站仍然拦——那是真实且可解释的边界。
>
> 教训不在 CSP，在**「报错信息要读完」**：前半句符合预期的时候，人不会去看后半句。

下面这段仍然成立（大站确实禁 `unsafe-eval`）：

```
Evaluating a string as JavaScript violates the following Content Security Policy
directive because 'unsafe-eval' is not an allowed source of script
```

**但 `chrome.scripting.executeScript({func, args})` 不受影响**——
注入的是编译好的函数，不是「字符串变代码」。

所以正确的设计不是想办法执行任意代码，而是
**把能力拆成一组参数化的固定操作**：`query(selector)`、`fetch(url)`、
`network(filter)`。绕过 CSP 只是顺带，更重要的是这样的能力对 agent 更好用、
对用户更安全——它不能执行任意代码。

`eval` 保留，但只在无 CSP 的小站有意义，工具描述里已写明。

## 五、滚动：三个必须同时做对的细节

「滚到底了但没加载更多」有三种成因，缺一个都会误判：

1. **滚错容器**。页面常有多个嵌套滚动区，只挑 `scrollHeight` 最大的那个
   经常挑错。→ 全部滚一遍，成本可忽略。
2. **只改 `scrollTop` 唤不醒监听 `wheel` 的虚拟列表**。
   → 补 `WheelEvent` 和 `scroll` 事件。
3. **只判一轮高度就收手**。懒加载常有一轮延迟。
   → 连续两轮不增长才算到底。

工具返回值里要报告**实际滚了哪些容器**（`div.content(2414)`）。
没有这个诊断，agent 只能瞎试。

> **能力必须自带诊断信息**——这条比上面三条都重要。工具失败时只说「失败了」，
> agent 就会开始撞运气；说清「我滚了 div.content，高度没变」，它才能换策略。

## 六、硬边界：扩展够不着的地方

小红书「导出数据」点下去，弹出的是 **macOS 原生的保存文件对话框**。
那不是网页 DOM，是操作系统的窗口，扩展完全够不着。

同类边界还有：
- 系统文件选择 / 保存对话框
- 浏览器原生 UI：下载栏、地址栏下拉、权限弹窗（摄像头/通知/位置）
- `chrome://` 和 Chrome 应用商店页面（浏览器禁止注入）
- 系统级权限授权窗口

**处理方式**：识别出来，明确告诉用户「这一步需要你点一下」，
不要在那儿反复重试。产品侧的缓解办法是引导用户在 Chrome 设置里
关掉「下载前询问每个文件的保存位置」，之后下载会直落默认目录，
`chrome.downloads` 就能拿到路径。

## 七、不抢用户的焦点

`captureVisibleTab` 截的是「那个窗口当前可见的标签页」，不是受控标签页。
用户切走后直接截图，截到的是他自己正在看的页面——曾经把私人笔记
送进过 agent 的上下文。

**规则**：
- 新标签页一律 `active:false` 后台打开
- 「受控」和「前台」是两件事，切换受控目标不动用户视线
- 除 `screenshot` 外，所有工具在后台标签页上都正常工作
- 需要前台时必须显式传 `focus:true`，并且工具描述里写明这会打断用户

## 七之一、标签页纪律：开页即登记，多线必显式

一次真实事故（2026-08-29，VFS 签证表）：主 agent 在 A 页填表，派出去的
subagent 一句 navigate 把「缺省槽」导去了 VFS——主 agent 下一条不带 tabId 的
命令就落进了 subagent 的页面。根因：**Claude Code 的主 agent 和 subagent 共用
一条 MCP 连接，在扩展眼里是同一个会话**，会话级隔离在父子之间天然失效，
且扩展侧无解（工具调用不携带 caller 身份）。

同一晚的另一面：多线自救（显式 tabId 分页干活）会让页面标记消失——归属以前
只从「每会话一个槽」反推，显式 tabId 驱动的页面从不进槽，于是没有光标、
没有驾驶舱、没有标签组，别的会话还能把它「继承」走。

现在的机制（v0.9.1）：

- **户口簿**（`ownTabs:<sid>`）：会话对某页发过命令就登记。标记、冲突检测、
  继承拦截都从「槽 + 户口簿」反推——显式 tabId 驱动的页面不再裸奔。
- **出生证**：`tabs(action:"new", label:"哪条线")` 回执带 `[tabId]「label」`，
  并提醒显式 tabId 用法。label 显示在 list、页内驾驶舱、胶囊空闲态。
- **找回**：`tabs(action:"list")` 标出 `*` 缺省槽、`+` 本会话的其他工作线、
  `×` 别的会话在用，加 label——上下文被压缩后从这里重建工作记忆。
- **当面提醒**：户口簿里 ≥2 页还走缺省槽的命令，回执尾部提醒切显式
  （10 分钟冷却，多线是持续状态，每条都唠叨会变背景噪音）。

**agent 侧的规则**（STRATEGY 的 TAB DISCIPLINE 段）：开页带 label，把返回的
tabId 转述进自己的回复（活过上下文压缩）；两条工作线一出现（派 subagent、
双账号并行），每条命令显式带 tabId；派 subagent 必须交接 tabId + label +
账号身份（模板见 `docs/双脑.md`）。

## 七之二、第二轮实战补充（X / 公众号图文）

### 接口名不要靠记忆猜

X 的用户时间线接口叫 **`UserOriginalsTimeline`**，不叫 `UserTweets`。
按记忆里的名字去 `network body:"UserTweets"`，得到的是 0 字节和一串
「解析失败」——而真正的接口就在同一份列表里躺着，243KB。

**永远先不带 body 调一次 `network`，按响应大小排序看实际请求。**

### 分页接口只差一个 cursor

同一个接口翻页时会被调很多次，URL 几乎一样。`network body:` 默认只给最后一条，
只取它 = 只拿到最后一批。用 `index` 从最新往回数，逐批取完。

### 三个产品 bug，都属于「静默出错」这一类

它们的共同点是**不报错、结果看起来正常**，这类 bug 最贵：

1. **stdout 异步截断** —— `console.log(大字符串)` 后立刻 `process.exit(0)`，
   没写完的部分被丢弃。167KB 的响应被截成 61KB，JSON 只是"恰好"损坏。
2. **自动修复销毁已有状态** —— 扩展重载会清掉 `registerContentScripts`，
   于是 `ensureNetHook` 判定「首次注册」并自动刷新页面，把辛苦滚出来的
   几百 KB 网络记录一起冲掉。**自动修复动作必须先检查现状再动手。**
3. **响应串号** —— 桥的 pending 只按消息 id 索引，而每个 agent 进程的 id
   都从 `c1` 开始。两个会话并发时后者覆盖前者，**响应会串到别人的请求上**。
   已改为按「连接序号:id」索引，并加了回归测试。

### 二进制有两条路，按大小分

- `fetch binary` 走 base64 over WebSocket，**上限 12MB**，好处是能精确指定落盘路径
- `download` 走 `chrome.downloads`，浏览器原生下载，无大小限制，
  且 `saveAs:false` **不弹系统保存对话框**——正好绕开第六节那条硬边界

三个 4K 视频最初下载失败，就是撞在 base64 通道上。现在超限会明确报错并指向 `download`。

### 跨域二进制必须从扩展侧发

图片几乎总在另一个域（公众号正文在 `mp.weixin.qq.com`，图在 `mmbiz.qpic.cn`），
在页面上下文 fetch 会被 CORS 挡死。扩展有 `host_permissions`，不受此限。
所以 `binary` 默认走扩展；少数认 Referer 的图床才用 `via:"page"`。

### 懒加载图片的真地址在 data-src

`src` 是 1px 透明占位符。不取 `data-src`，导出的 markdown 里
每张图都会变成同一个像素。

### 文件上传：DataTransfer 是唯一的路

网页只认「用户选了文件」这个事件，而系统文件对话框是扩展够不着的。
造一个 `File`，用 `DataTransfer` 塞进 `input.files` 再触发 change——
这是把图片送进网页编辑器的唯一办法，且属于 L1，不需要 debugger。

### 「后台工作」的例外

X 在标签页不可见时**根本不发** timeline 请求。诊断顺序：
① 切前台看是否恢复 → ② 还不行就刷新（SPA 首次路由初始化问题）。
两步走完再换思路，别在第一个假设上耗着。

## 七之三、第三轮：主动造场景撞出来的（2026-08-26）

前两轮都是被真实任务推着走。这一轮换了方法：先建一个**本地靶场**
（`test/fixtures/playground.html`，无 CSP、带事件记录仪），把典型交互一个个摆出来撞。
效果比等任务好得多——下面五条里有四条，真实任务半年也未必碰得到，但一碰就是静默失效。

### 1. 合成点击必须发完整的事件序列

真实点击浏览器会依次发出
`pointerover → mouseover → mousemove → pointerdown → mousedown → focus → pointerup → mouseup → click`，
而 `el.click()` **只发最后那一个**。

react-select、Ant Design、Element UI、MUI 的下拉菜单全都绑在 `mousedown` 上，
所以「点了下拉没反应」是这条的必然结果，而且不报错——快照里 `expanded` 一直是 false。

### 2. 焦点该不该动，看 mousedown 有没有被 preventDefault

浏览器的规则是：**mousedown 没被拦下，才移动焦点**。
自管焦点的组件（react-select 就是）正是靠拦下 mousedown 再自己 `focusInput()` 来打开菜单的。
工具无条件 `focus()` 会把它刚设好的焦点抢回来，菜单于是永远打不开。

### 3. 事件目标是最内层元素，不是你 resolve 到的那个

真实点击的 `event.target` 是光标下最内层的元素，再往上冒泡。
组件按 `event.target.tagName` 分支的逻辑（react-select 就有）会因此走进另一条路。

**但改成派发到最内层之后立刻踩了第二个坑：`<svg>` 元素没有 `click()` 方法。**
图标按钮的最内层几乎总是 `<svg>`/`<path>`，于是全网的图标按钮一律
`el.click is not a function`。正解是派发合成 `click` 事件——规范上它会在事件目标
最近的可激活祖先上执行激活行为，这正是真实点击落在 `<a>` 里的 `<span>` 上也能跳转的原因。

### 4. 后台标签页不产生渲染帧 —— 这条影响最大

实测：`scrollTop` 从 0 改到 298，**scroll 事件计数是 0**；手动派发一次，懒加载立刻补货。

原因是 scroll 事件在帧生命周期里派发，而后台标签页不产帧。
这和第七之二节记的「X 在标签页不可见时根本不发请求」是同一个根因。

因为「不抢用户焦点」是这个产品的硬规则，**后台能滚动这件事必须自己兜住**：
改完 `scrollTop` 之后，往每个容器补发 `wheel` 和 `scroll`（scroll 在元素上不冒泡，
必须逐个发）。改完之后后台标签页里从 20 条滚到了 100 条。

**兜不住的那部分要说清楚**：用 `IntersectionObserver` 判断加载时机的列表，
后台标签页里观察器根本不回调，补发事件也没用——只能 `focus:true` 切到前台，
代价是打断用户。工具在高度没涨时会把这三种可能一起报出来。

**同一个根因带来一个意外的好处**：Chrome 不给后台标签页弹 `alert`/`confirm`，
所以「弹窗挡住一切、扩展彻底失联」这个经典死锁，在后台工作模式下自动免疫。
只有为截图切到前台时才需要提防。

### 5. 快照里「同一个可点区域算两次」不只是费 token

`<button>` 里的 `<i class="fa"> Login</i>` 靠 `cursor:pointer` 混成第二个候选，
`<label for=x>` 又是输入框的代言人——它们给 agent 提供了一个点了不管用的选项。
登录页从 7 个元素降到 4 个，名字一个没少。

区分「弱候选」（只靠 `cursor:pointer` 进来的）很重要：带 `onclick`/`tabindex` 的元素
即使嵌在链接里，也可能是独立的操作（卡片上的「×」关闭），丢了就没了。

### 6. iframe 不注入就等于不存在

支付、验证码、OAuth、嵌入式编辑器几乎全在 iframe 里。
现在注入走 `allFrames: true`，子框架的元素在快照里写成 `e5@f2`，
桥接层按后缀路由、把 ref 还原、换上那个框架自己的 snapshotId。

**agent 面对的协议一点没变**——content script 不知道有框架这回事，
`click`/`type`/`fill`/`key` 一行都没改。跨源 iframe 同样有效。

### 7. 字段名比想象中更难拿

`input[type=file]` 被 `roleOf` 归到 textbox，是个静默陷阱：agent 看见 textbox 就去 type，
而往 file input 写字符串什么都不会发生。

还有两类拿不到名字的：react-select 把占位符放在单独的 div 里用 `aria-describedby` 指过去；
更常见的是标签和输入框并排放在一个 `.form-group` 里，谁也没写 `for`。
补了这两条之后，demoqa 那张出了名难搞的注册表，每个字段都有了正确的名字。

## 八、决策树（agent 该背下来的）

```
要操作（点、填、走流程）
  ├→ snapshot → click / fill / key
  ├→ 填表        fill 一次填完（type 一个字段一份快照，10 个字段白扔上万 token）
  ├→ ref 带 @fN  子框架里的元素，照原样传，桥接层自己路由
  ├→ 自定义下拉  不是 select：click 展开 → 从返回的快照里读选项 → click 选中
```
