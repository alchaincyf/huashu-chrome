# 双脑模式（可选）：主脑定计划，快脑跑循环

> 这是**可选加速器，不是运行前提**。huashu-chrome 的全部能力——act 剧本、
> learnings、教练、ask——在单脑下完整可用。宿主环境起不了 subagent？
> 什么都不用做，也什么都不会少。

## 为什么

实测归因（见 `_notes/规划-v1.0-速度.md`）：浏览器任务 98% 的墙钟耗在命令之间的
模型回合上。回合成本由两个因子决定——回合数（act 剧本负责压）和单回合耗时。
后者取决于跑循环的是哪个模型：浏览器驱动是大量的小决策（「下一个字段填哪个」），
很少需要主模型的全部深度。把循环交给一个便宜快模型，回合从 ~20 秒降到 2–4 秒。

## 能力自适应：怎么对所有用户都有好体感

原则一句话：**agent 自己最清楚自己有没有 subagent 能力，所以探测在提示层做，
不进协议**。

- 机制是 STRATEGY 里的「OPTIONAL FAST LOOP」段，第一句就是门槛：
  「只有宿主能起 subagent 才读本段，否则整段忽略」。
- 起得了的（Claude Code 的 Task、各类支持 sub-session 的宿主）→ 自动获得加速；
  起不了的（Codex CLI、Kimi、纯 MCP 客户端）→ 这段话是零字节的空气，
  没有报错、没有降级、没有「你的环境不支持 XX」的噪音。
- 协议层（桥、扩展）完全不感知宿主用几个脑：快脑连上来就是一个普通会话，
  隔离、标记、审计、敏感闸全部照旧生效。

**但有一个例外必须直视：Claude Code 的主 agent 和 subagent 共用同一条 MCP 连接，
在扩展眼里是同一个会话（sid 按 MCP 进程的父 pid 生成）。** 会话级隔离（缺省槽、
冲突拦截）在父子之间全部失效——subagent 一句 navigate 就能把共享的缺省槽改写，
主脑下一条不带 tabId 的命令就落进 subagent 的页面。这在扩展侧无解（工具调用
不携带 caller 身份），唯一的防线是纪律：**多线并行时每条命令显式带 tabId**。
扩展会在「户口簿里有 ≥2 页却走缺省槽」时当面提醒（10 分钟冷却）。

不做的事：不做「环境探测 API」，不做双脑专属命令，不在扩展里区分主脑快脑——
任何一条都会让单脑路径变成二等公民，违背「所有 agent 用户都有好体感」。

## Driver 提示词模板（主脑起 subagent 时抄这份）

```
你是浏览器执行手，通过 huashu-chrome 的 MCP 工具操控用户的真实 Chrome。

任务目标：<主脑填：一句话目标 + 完成判据>
背景约束：<主脑填：站点、账号语境、已知注意事项>
你的标签页：<主脑填：tabId + label + 这页登录的是谁的账号。
  没给就自己 tabs(action:"new", url:…, label:"哪条线") 开一个，把返回的 tabId 记下来>

规矩：
0. 只许动你的标签页，**每条命令都显式带 tabId**——缺省槽和主脑共用，
   谁都可能改写它。要开新页自己 new 并带 label，忘了就 tabs(action:"list")。
1. 开工先 learnings(domain) 查经验；有 ```act 剧本就填好占位符直接跑。
2. status 先声明你准备做什么（一句话，用户看得到）。
3. 默认用 act 批处理，翻页用 repeat，可选弹窗用 if，状态检查用 assert；
   单发 click/type 只用于真正无法预判的下一步。
4. 标签页保持后台，不抢焦点；需要用户帮忙（验证码/扫码/OTP）就 ask，
   把 ask 的结果如实带回。
5. 以下情况**停下来，把现场汇报给主脑，不要自作主张**：
   支付或敏感提交被拦、计划需要改变、连续两次同一步骤无效果。
6. 收工把学到的规律（含跑通的剧本）save 回 learnings。

汇报格式：做成了什么（判据核对）/ 关键数据 / 卡在哪（若有）/ 回流了什么经验。
```

## 验证方式

同一个基准任务（如多页表单）分别单脑、双脑各跑一遍，用审计归因脚本
（`~/.huashu-chrome/audit.jsonl`）对比：总墙钟、回合数、空档中位数、错误率。
不认体感，认数字。
