# 架构 v0.3：可靠性三件套

这一版只做三件事，但这三件事一起决定了「这个产品能不能替人干活」：

| | 现在 | v0.3 |
|---|---|---|
| **点得动吗** | 合成事件，`isTrusted:false`，四类场景过不去 | L1 默认 + L2 按需真实事件 |
| **知道点没点动吗** | `sleep(400)` 后回一份快照，agent 自己看 | 每个写操作返回效果证据；零证据明确报错 |
| **卡住了怎么办** | 验证码/扫码/OTP 前面无解，只能放弃 | `ask` 请用户接管，四态返回 |

三件事不是三个独立特性。**效果证据是 L2 的触发信号，L2 是效果证据的兜底手段，
而两者都失败时才轮到人工介入。** 它们串成一条链，这是本版设计的主轴：

```
L1 执行 → 采集效果证据
            ├─ 有证据 → 返回（并早停，比现在的固定 sleep 更快）
            ├─ 零证据 → 升级 L2 重试一次 → 再采证据
            │             ├─ 有证据 → 返回，并说明「L1 无效，L2 生效」
            │             └─ 仍零证据 → 报 NO_EFFECT + 诊断
            └─ 需要人（验证码/登录/风控） → ask 交还控制权
```

## 一、L1 / L2 分层执行

### 1.1 为什么必须有 L2

`content.js` 现在把合成事件做到了能做的极限——九个事件按真实顺序派发、
`elementFromPoint` 修正 target、`mousedown` 被 `preventDefault` 时不抢焦点、
`emulateDefault` 手工补上浏览器该做而合成事件不做的默认行为。

这些都对，但它们绕不开一个事实：**`isTrusted:false`**。四类场景因此结构性失效：

| 失效场景 | 现在的表现 | 根因 |
|---|---|---|
| 风控站点的关键动作（下单、提现、发布） | 事件被静默忽略，页面无反应 | 站方直接检查 `event.isTrusted` |
| 自管输入的编辑器（Monaco、CodeMirror、飞书/Notion 富文本、IME 组合态） | `applyText` 写进 DOM，编辑器内部状态没变，一失焦就回滚 | 编辑器状态在 JS 里，不在 DOM 上 |
| 文件对话框 | `doUpload` 靠 `DataTransfer` 伪造 FileList | 系统对话框在浏览器进程里 |
| 需要用户手势的 API（剪贴板写入、全屏、`window.open`） | 静默被拦 | 浏览器要求 transient user activation |

`content.js:628` 那段注释已经写明了其中一条。剩下三条同源。

### 1.2 L2 顺带解决的四个现存缺陷

L2 的投入回报远不止「点得动」。attach 之后这些当场就通了：

| 现存缺陷 | 位置 | L2 怎么解 |
|---|---|---|
| 截图必须把标签页切前台，会打断用户 | `background.js` `screenshot` | `Page.captureScreenshot` 可截后台标签页 |
| `eval` 在有 CSP 的大站全废 | `background.js` `eval` | `Runtime.evaluate` 不受页面 CSP 管 |
| `alert`/`confirm` 弹出后整条链路卡死 | `DIALOG_BLOCKING` 有错误码但无实现 | `Page.javascriptDialogOpening` 事件 + `handleJavaScriptDialog` |
| `upload` 靠 `DataTransfer` 伪造，站点校验 `isTrusted` 就失效 | `content.js` `doUpload` | `DOM.setFileInputFiles` 是浏览器原生路径 |

**其中「后台截图」和「弹窗不再卡死」是能直接写进 README 的用户可感差异。**

### 1.3 权限策略：默认不要 `debugger`

`debugger` 权限会让安装时的警告文案变成「调试器」级别，商店审核也更严。
所以它进 `optional_permissions`，不进 `permissions`：

```jsonc
{
  "permissions": ["tabs", "scripting", "storage", "alarms", "downloads"],
  "optional_permissions": ["debugger"]
}
```

- 默认安装 = 现在的权限集，警告文案不变
- 首次需要 L2 时，SW 里 `chrome.permissions.contains({permissions:['debugger']})` 为 false
- **`chrome.permissions.request()` 必须在用户手势里调用**，SW 响应 agent 命令时没有手势 →
  所以走这条路：SW 弹一条 `chrome.notifications` +
  popup 里常驻一个「启用高保真模式」开关，用户点一次，永久生效
- 未授权时 L2 不可用，工具返回 `NEEDS_L2` 错误码，文案告诉 agent「让用户去扩展弹窗点一下」

这比 BrowserSkill 好：它的扩展安装时就必须给 debugger 权限，没有选择。

### 1.4 attach 生命周期：粘性 + 空闲释放

attach 有两个成本：约 100–300ms 握手，以及那条「已开始调试此浏览器」的黄带子。

- **不能用完就 detach**：连续五次 L2 点击会闪五次黄条，比常驻还难受
- **不能常驻**：那就退化成 BrowserSkill 了

策略：**首次 L2 操作时 attach，之后保持；`L2_IDLE_MS = 5000` 内没有新的 L2 操作则自动 detach。**
一串连续操作 = 一次黄条，几秒后自动消失。

其它必须处理的生命周期事件：

| 事件 | 处理 |
|---|---|
| 用户自己打开了 DevTools | attach 抛 `Another debugger is already attached` → 降级回 L1 并在返回里说明，不报错误终止 |
| 用户手动点了黄条上的「取消」 | `chrome.debugger.onDetach` → 清状态，下次操作重新 attach（若又被拒则降级 L1） |
| 标签页关闭 | `onDetach` 事件里清理 |
| SW 被回收 | attach 状态由浏览器持有，SW 醒来后 `chrome.debugger.getTargets()` 可重建，不依赖内存变量 |

### 1.5 ref → 坐标的交接（L1 和 L2 的分工）

**L2 不重新实现元素定位。** 快照、refMap、可见性判定、遮挡检测全部留在 content script，
L2 只接管「派发事件」这一步：

```
background: 收到 click(ref=e3)
  → content script: __hc:'locate' ref=e3
       解析 ref（走现有 resolve()，含全部防呆）
       scrollIntoView + 遮挡检测（走现有逻辑）
       返回 { x, y, tag, role, canL1 }        ← 视口坐标，CSS px
  → background: chrome.debugger Input.dispatchMouseEvent(x, y)
```

两个必须守住的约束：

1. **取坐标和派发之间不能有等待。** 中间只要有 `await sleep()`，页面一滚动坐标就废了，
   点到的是别的东西。`locate` 返回后立刻派发，不做任何其它异步操作。
2. **坐标单位是 CSS px、相对视口左上角**，正是 `getBoundingClientRect()` 的口径，
   与 CDP `Input.dispatchMouseEvent` 一致，不需要乘 DPR。

### 1.6 后台可用性：已实测确认（2026-08-26）

原假设「CDP 输入在后台标签页是否有效」是整个 L2 的成败前提——若必须切前台，
L2 就和「不打扰用户」的硬规则直接冲突。在 `playground.html` 的事件记录仪上实测：

| 条件 | 结果 |
|---|---|
| 后台标签页，**不开**焦点模拟 | `mouseMoved` 送达（`isTrusted` 已是 true），下一发 `mousePressed` 直接打断调试会话，报 `Detached while handling command`。只有 pointerover/mouseover/mousemove 落地，点击等于没发生 |
| 后台标签页，**开** `Emulation.setFocusEmulationEnabled` | 九个事件完整送达，全部 `isTrusted:true`，`focus` 和 `click` 都在 |
| 前台标签页 | 同上，完整 |

**结论：`Emulation.setFocusEmulationEnabled({enabled:true})` 是后台 L2 的必要条件**，
已固化进 `cdp.js` 的 `ensureAttached`。detach 时浏览器自动恢复真实焦点状态。

这条实测结果直接决定了产品形态：**我们能在后台标签页派发真实事件，
BrowserSkill 必须开一个用户看得见的 Agent Window。同样的 `isTrusted`，我们不打扰。**

其余实测结论：

- `Input.insertText` 写入成功，走浏览器文本管线（富文本编辑器要靠它）
- `Tab` 键产生原生焦点移动，不需要 L1 那套 `emulateDefault` 手工模拟
- 只认 `mousedown` 的自定义下拉（react-select 那类）L2 一击即中，
  不需要 L1 的 `retryCombobox` 猜箭头启发式

### 1.6.1 ⚠️ 反例：原生 `<select>` 必须留在 L1

实测推翻了设计初稿里「原生 select 该走 L2」这一条：

L2 点击原生 `<select>` 会打开**浏览器进程渲染的原生下拉 popup**，
它不在页面渲染树里，CDP 的 `Input` 域打不到它——键盘事件被 popup 吃掉，
`value` 不变，而且下拉停在打开状态阻塞后续操作。

L1 的 `applySelect`（直接设 `value` + 派发 `change`）才是原生 select 的完整语义。
**所以 `<select>` 在预判里强制走 L1，且必须挡住自动升级**——
否则 L1 成功后若证据判定失误触发升级，反而会把一个已经选好的下拉点开卡住。

### 1.7 什么时候升级：预判 + 失败重试，但敏感动作除外

两条触发路径：

**A. 预判（执行前）** —— `locate` 返回 `prefer: 'L1' | 'L2' | null`：

| 目标 | prefer | 理由 |
|---|---|---|
| 原生 `<select>` | **强制 L1** | §1.6.1，L2 会把它卡在打开状态 |
| `input[type=file]` | L2 | `DOM.setFileInputFiles` 是原生路径 |
| 在 `.monaco-editor` / `.CodeMirror` / `[data-slate-editor]` / `.ql-editor` 内 | L2 | 状态在 JS 里，改 DOM 会被回滚 |
| 其余 | null（走 L1，失败再升级） | 默认最省 |

**B. 失败重试（执行后）** —— L1 跑完，效果证据为零 → 自动升级重试一次。

**B 有一个必须挡住的风险：重复执行。**
L1 可能实际生效了但检测不到（纯 JS 副作用、异步请求已发出但 DOM 未变），
这时自动 L2 重试就是点了两次——在真实登录态下可能是两笔订单。

所以自动升级有一道确定性闸门（不问模型）：

```
命中敏感特征的目标，永不自动升级，只报告并建议 agent 显式重试：
  · 按钮文案含 提交/支付/付款/下单/确认/删除/发布/转账/购买/立即
  · type=submit 或在 <form> 内且是唯一提交按钮
  · 目标或祖先带 [data-testid*=submit]、[class*=pay]、[class*=submit]
```

非敏感目标（展开下拉、切换标签、勾选、输入）自动升级，因为重复执行是幂等的。

agent 侧还有一个显式逃生舱：所有写操作接受 `real: true`，直接走 L2，跳过预判和重试。

## 二、效果证据：不替模型下判断，但绝不让「什么都没发生」蒙混过去

### 2.1 现状

`background.js` 的 `click` / `type` / `fill` / `key` 现在做的是：
固定 `sleep(400)` → 比对 URL → 回一份新快照。

问题有三个：
- **只看 URL 一个维度**，SPA 里绝大多数交互不改 URL
- **固定等待**：快页面白等 400ms，慢页面 400ms 不够，两头都不讨好
- **无变化和有变化返回的东西长得一样**，agent 只能自己比对两份快照——而它通常不会比

### 2.2 采什么证据

`locate` 时记录基线，动作后轮询比对。全部在 content script 里做（只有它看得见 DOM）：

| 维度 | 怎么测 | 为什么需要它 |
|---|---|---|
| `url` | background 侧 `chrome.tabs.get` | 跳转类操作 |
| `dom` | 元素总数 + 可交互元素数 + `body.innerText.length` | 弹层出现、列表加载、内容替换 |
| `target` | 目标元素的 `aria-expanded` / `checked` / `value` / `class` | 下拉展开、勾选、受控组件回滚 |
| `alerts` | 复用现有 `collectAlerts()` | **校验错误是表单流程的头号失败模式** |
| `focus` | `document.activeElement` 变化 | 焦点转移类操作 |
| `dialog` | L2 已 attach 时监听 `javascriptDialogOpening` | 原生弹窗 |

### 2.3 判定规则：分级，不是二值

**不替模型下「成功/失败」的判断**——那需要理解意图，扩展没有意图。
扩展只回答一个确定性问题：**页面到底动没动。**

```
有任一维度变化  → effect 段落如实列出变化，早停返回（不等满）
全维度零变化    → 明确的一句话 + 诊断 + 建议，而不是一份看着正常的快照
```

零变化时的返回长这样：

```
⚠️ 点了 [e7]，但页面完全没有反应（DOM、URL、焦点、目标状态、页面提示均无变化）。
可能是：① 事件被站点的 isTrusted 检查忽略 —— 已自动用真实事件重试，仍无效；
② 这个元素只是容器，真正的按钮在它内部或旁边；③ 操作确实发生了但只有异步副作用。
```

有变化时附在快照前面：

```
[e7] 已点击 · 效果：DOM +14 节点，aria-expanded false→true，焦点移到 input[name=city]
```

**这段文字的价值不在人类可读，在于它把「静默」变成了「显性」。**
agent 读到「完全没有反应」会换策略；读到一份长得正常的快照只会往下走。

### 2.4 早停带来的顺带收益

轮询窗口 `0 → 1200ms`，每 100ms 检查一次，任一维度变化立即返回。

- 快页面：约 100–200ms 返回，比现在的固定 400ms **更快**
- 慢页面：最多等 1200ms，比现在的 400ms **更稳**
- 导航类操作仍走 `waitForLoad`，不受此窗口限制

即「更可靠」和「更快」在这里不冲突，是同一个改动的两面。

### 2.5 噪声控制

页面上的时钟、轮播、埋点会让 DOM 一直在变，判定必须避免「永远有效果」：

- DOM 变化设阈值：节点数变化 `>= 3` 或 `innerText.length` 变化 `>= 20` 才算
- 只在动作发生后的窗口内比对，不做长期观察
- `target` 和 `alerts` 两个维度权重最高（它们几乎不可能是噪声），
  只有这两个维度变化时即使 DOM 阈值没过也算有效果

## 三、人工介入：`ask`

### 3.1 定位

产品里第一个**长阻塞 + 需要用户交互**的命令。用途：验证码、扫码登录、
短信 OTP、支付确认、以及任何 agent 判断「这一步该由人来」的时刻。

### 3.2 为什么我们的形态比 BrowserSkill 更短

BrowserSkill 必须把用户从他自己的窗口拽到 Agent Window 去解验证码。
我们本来就在用户自己的浏览器里，路径短一半：切前台 + 高亮 + 一个不挡内容的浮条。

**这是全项目里唯一一个「抢焦点是正确的」的场景**——正在请用户帮忙，
他理应看到那个页面。其它所有工具继续守「不抢焦点」的硬规则。

### 3.3 协议

```jsonc
// agent → 扩展
{ "cmd": "ask", "params": {
    "prompt": "请完成滑块验证，通过后点「我完成了」",
    "title": "需要人工验证",              // 可选
    "targets": ["e7", "#submit"],         // 可选，ref 或 selector，滚动到并闪烁高亮
    "timeout": 300000,                    // 默认 5 分钟，桥上限 600s
    "until": { "urlContains": "/dashboard" }  // 可选，自动完成判据
} }

// 返回
{ "outcome": "continued|cancelled|timed_out|completed", "note": "用户回填的文字", "waitedMs": 41200 }
```

四态照搬 BrowserSkill 的语义。这个 API 设计是对的，没必要为不同而不同——
`continued`（用户点了完成）/ `cancelled`（用户拒绝，agent 应中止而非重试）/
`timed_out` / `completed`（`until` 判据自动命中）。

`cancelled` 和 `timed_out` 必须区分：前者是明确的「不要做这件事」，
agent 收到应当停止整个任务；后者只是没人在。

### 3.4 UI：浮条，不是遮罩

BrowserSkill 用的是覆盖式遮罩，仓库里已经有 issue 抱怨它挡住内容。我们做浮条：

- 右下角固定浮层，最大宽度 380px，不阻挡页面交互（页面必须可交互——用户要去解验证码）
- 顶部一行标题 + prompt 正文 + 一个可选输入框（回填 `note`）+ 「我完成了」「取消」两个按钮
- `targets` 里的元素：`scrollIntoView` + 两秒描边闪烁，让用户不用找
- 同步发一条 `chrome.notifications`——用户很可能根本不在浏览器里

样式必须**全部内联 + 极高 z-index + `all: initial` 隔离**，
不能被页面 CSS 污染（这类浮层被站点样式击穿是常见故障）。

新增文件 `extension/ask-overlay.js`，独立于 `content.js`，按需注入。
理由：`content.js` 现在 1051 行且全是无 UI 的纯逻辑，把 DOM 渲染混进去会让它变成两个东西。

### 3.5 SW 存活与状态

阻塞 5 分钟期间 SW 可能被回收，内存里的 pending Promise 会一起消失。

- 现有 `PING_MS = 20000` 的 WS ping 已经能重置 SW 的空闲计时（Chrome 116+），
  这是主要保障
- 兜底：`ask` 的会话状态（cmd id、路由键、tabId、deadline）写进 `chrome.storage.local`，
  SW 复活后能把结果补发回桥
- 桥侧：`ask` 命令带 `timeout` 参数走已有通道（`bridge.js` 上限 600s，够用），
  不需要改桥的超时逻辑

### 3.6 无人值守

服务器/定时任务场景没有人可问。环境变量 `HUASHU_CHROME_ASK=off` 时，
`ask` 立即返回 `{outcome:"disabled"}`，agent 不该重试，应当自行完成或干净地停止。

### 4.1 新的执行路径

所有写操作（`click`/`type`/`select`/`fill`/`key`/`upload`）收敛到一个函数：

```
perform(tabId, cmd, params):
  1. locate      → content script 解析 ref、滚动、遮挡检测、返回坐标 + 基线 + canL1
  2. 选层         → params.real → L2
                    canL1 === false → L2
                    否则 → L1
  3. 执行         → L1: 现有 content script 动作（一行不改）
                    L2: cdp.js 派发真实事件
  4. 采证据       → 轮询 effect 比对，最长 1200ms，有变化早停
  5. 零证据且允许升级 → 回到 3 走 L2，再采一次证据
  6. 组装返回     → effect 段落 + note + 新快照
```

现有 `content.js` 的 `doClick`/`doType`/`doFill`/`doKey` **一行都不改**，
它们继续是 L1 的实现。新代码全部加在它们外面。这是本次改动能控制住风险的关键。

## 五、需要拍板的三个点

1. **自动升级的默认值**：默认开（agent 无感，但敏感动作走确定性闸门挡住）
   / 默认关（必须显式 `real:true`）。文档按「默认开」写。
2. **L2 权限**：`optional_permissions` 引导用户点一次（安装警告轻）
   / 直接进 `permissions`（少一步，但安装警告变重、商店审核更严）。文档按前者写。
3. **`ask` 抢焦点**：默认切前台（用户在请求帮忙时理应看到）
   / 只发通知不切前台（更克制，但用户可能一直看不到浮条）。文档按前者写。

## 六、验收标准

这一版做完，下面每条都要能在 `playground.html` 或真实站点上演示：

- [ ] 后台标签页里，CDP 派发的点击 `isTrusted` 为 true 且触发默认行为（§1.6 实验）
- [ ] 原生 `<select>` 能真正展开并选中，不只是改 value
- [ ] 点一个「什么都不做」的按钮，返回明确的「页面完全没有反应」而不是一份正常快照
- [ ] 表单校验失败时，`alerts` 出现在效果证据里，agent 不会误以为提交成功
- [ ] 触发 `alert()` 后链路不再卡死
- [ ] 后台标签页截图成功，不打断用户
- [ ] 有 CSP 的站点上 `eval` 可用
- [ ] `ask` 四态全部可复现，含 `until` 自动完成
- [ ] 未授权 debugger 时，L2 失败降级为清晰的 `NEEDS_L2` 提示，链路不中断
- [ ] 用户开着 DevTools 时，L2 自动降级 L1 并说明，不报错终止
