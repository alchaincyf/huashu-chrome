# v0.4 规划：把回合数降一个数量级

## 一、为什么是这件事

体验差距有三个轴，v0.3 动了两个：

| 轴 | 状态 |
|---|---|
| 静默失败 | ✅ v0.3 的效果证据 + 自动升级 L2 |
| 打扰度 | ✅ 后台标签页 + 后台真实事件 + 后台截图，本来就领先 |
| **回合数** | ❌ **没动过。这是最大的一块** |

一个「登录后台 → 找到某条内容 → 改标题 → 保存」的任务，现在长这样：

```
snapshot → click → 快照 → click → 快照 → type → 快照 → click → 快照   ≈ 8 次调用
```

每一次都是：一次模型推理 + 一份 1–2k token 的快照回传。而中间那几份快照，
**agent 通常根本不看**——它在发出 click 之前就知道下一步要点什么了。

这不是我们做得差，是「一个工具调用 = 一个原子动作」这个范式的固有成本，
所有走这条路的产品都一样（BrowserSkill 因为是 CLI，每步还多一个进程启动）。

10 倍体验就藏在这里：**把「执行 → 观察 → 决定」的循环从模型层下沉到扩展层**，
只在真正需要判断时才回到模型。同样的任务变成：

```
snapshot → act([...4 步...]) → 确认快照     ≈ 3 次调用
```

而且这件事**只有我们做得了**：CLI 一次调用一条命令，批处理要么写成 shell 循环
（每步还是回模型），要么推翻整个 CLI 范式。MCP 的 JSON schema 天然能表达动作数组、
每步断言、带分支的结果树。

## 二、`act` 的设计

### 2.1 最大的技术障碍：ref 会在中途作废

批处理的每一步都可能改变页面，而 ref 绑定在快照上——第二步开始，
agent 给的 ref 可能已经指向了别的元素，或者干脆不存在。

这是整个设计的核心难点，也是「为什么现在还没有人做好这件事」的原因。

**解法：两种定位方式并存，规则明确。**

| 定位 | 写法 | 何时有效 |
|---|---|---|
| ref | `{"do":"click","ref":"e3"}` | 页面结构没变时。第一步总是有效（agent 刚看过快照） |
| 语义 | `{"do":"click","find":{"role":"button","name":"下一步"}}` | 任何时候。页面重渲染后现场重新查找 |

**硬规则：某一步之后页面结构发生变化，后续步骤的 ref 全部作废，只有 `find` 能继续。**
作废时不静默跳过，而是明确停下来报告——让 agent 知道该用 `find` 重写这个序列。

给 agent 的心智模型很简单：

- **连续填表**（页面不变）→ 用 ref，最省
- **走流程**（每步都换页）→ 用 find，最稳

### 2.2 语义定位怎么查

复用快照已有的 `roleOf` / `accessibleName`，在页面上现场匹配：

```jsonc
{"role": "button", "name": "下一步"}          // 精确匹配可访问名
{"role": "textbox", "name": "手机号", "nth": 0} // 同名多个时取第几个
{"name": "提交"}                              // 省略 role，只按名字找
{"selector": "#submit"}                       // 兜底
```

匹配规则（按顺序）：全等 → 去空白全等 → 包含。命中多个且没给 `nth` 时**报错而不是猜**，
把候选列出来——猜错一个按钮的代价可能是一笔订单。

### 2.3 每步之间做什么

复用 v0.3 的 `settle`：执行 → 采效果证据 → 有变化就早停。

三种情况停止整个序列：

1. **某步执行失败**（元素找不到、被遮挡、不可交互）
2. **某步零效果**——先按 v0.3 的规则自动升级 L2 重试一次，仍无效果则停
3. **命中敏感动作**——见下

### 2.4 安全：批处理不能变成「一次授权做十件事」

这是 `act` 最大的风险。一个 prompt injection 让 agent 发出一串动作，
批处理会一口气全做完，中间没有任何人看得见。

**闸门（确定性，不问模型）：**

- 序列里任何一步命中 v0.3 的敏感特征（提交/支付/删除/发布 + form 内的 submit），
  **执行到那一步就停**，把剩余步骤原样返回，让 agent 单独调用 `click` 去做。
  单独调用意味着它会在返回里看到完整的效果证据，也意味着这一步在审计日志里独立可查。
- 序列长度上限 20 步。
- 每一步都照常写审计日志（`act` 不是一条记录，是 N 条）。
- `allowSensitive: true` 可以放行，但那是 agent 的显式声明，会被审计记下来。

### 2.5 返回什么

只回**一份**最终快照，这就是 token 节省的来源。前面加一段逐步回执：

```
act 完成 3/4 步：
  ✅ click "下一步"        效果：DOM +12 节点
  ✅ type  "手机号" ←11字   效果：value 空 → 138…
  ✅ click "同意条款"       效果：checked false → true
  ⏸ click "提交订单"       停在这里：这是提交类动作，批处理不代做。
                          单独调用 click 完成它。

（当前页面快照）
```

失败时同样把「做到哪一步、为什么停」讲清楚——批处理最怕的就是
「跑了一半，不知道跑到哪了」。

## 三、同期做的第二件事：敏感页面识别

2026-08-26 的真实事故：agent 以为还在 npm 的 access 页，那个标签页已经跳到
2FA 设置页，一次 `read_text` 把用户的 **2FA 恢复码**整页读进了对话上下文。

v0.3 已经补了「受控标签页漂移警告」——那是防「读错页面」。
但**读对了页面也可能读到不该读的东西**：token 列表、恢复码、私钥、密码框旁边的明文。

### 3.1 做法：不拒绝，而是隐去

全拒绝不实用（agent 有时确实需要在 tokens 页面上操作），所以：

- **内容层**：识别成组的高熵字符串（≥3 行、每行 ≥16 位的 hex/base32/base64），
  替换成 `[已隐去 N 组疑似凭据，需要请人工查看]`。其余内容照常返回。
- **URL 层**：命中 `/tfa`、`/2fa`、`/recovery`、`/backup-code`、`/tokens`、
  `/api-key`、`/security` 时，在返回顶部加一行提示，告诉 agent 这是凭据页面，
  不要把内容转述或写进文件。
- **密码框**：快照里 `type: password` 的输入框已经不回显值（v0.1 就做了），
  这次把它旁边可能的明文展示（「点击显示密码」展开后的文本）也纳入隐去范围。

误报的代价是「agent 少看到几行乱码」，漏报的代价是凭据泄露。**宁可误报。**

### 3.2 为什么这条值得做

没有任何竞品做这件事。而浏览器 agent 恰恰是最容易撞上凭据页面的形态——
它带着用户的完整登录态，在用户自己的浏览器里，而用户随时可能把标签页
切到设置页去。这是这个产品形态自带的风险，不是可选的加分项。

## 三之三、期间追加的第三件事：多 agent 连接级隔离

2026-08-26 真实事故：两个 agent 会话同时干活（一个操控签证页、一个操控小红书），
「受控 tab」是全机唯一的全局单值，一个会话的 `tabs(new/select)` 把另一个会话的
缺省调用拽到了自己的页面上。于是补了这一项——不在原规划里，但属于同一批交付：

- 桥给每条命令盖章 `connId`（连接序号），扩展为每个连接维护独立的受控 tab 槽
  `agentTab:<connId>`；`activeTabId` 降级为「最近受控 tab」，是新连接的继承源
- 新会话首次缺省调用继承全局槽，并在返回里提示尽早 `tabs(select)`
- select/close 别人正在操控的 tab：警告不阻止
- 漂移警告基线（`lastSeen`）也按连接分桶——A 的导航不再压制 B 的漂移提示
- agent 断线发 `agent_closed` 清槽，tab 关闭扫清全部槽

边界：同一 tab 上两个会话并发写入仍是「尽力而为」（共享快照，`STALE_SNAPSHOT` 兜底）；
升级前活着的旧会话仍共享全局槽，新开会话才有隔离。

## 四、不做什么

- **录制回放**（trace）——重，而且它的价值建立在「已经有一批稳定可复用的流程」之上，
  现在还没到那个阶段
- **站点白名单默认拒绝**——README 承诺过，但它会显著增加摩擦（每个新域名都要用户点一次），
  与「体验好 10 倍」直接冲突。发布前必须处理，但需要产品决策，不在这一版自作主张
- **upload 走 L2**——现有 DataTransfer 路径在实测站点上是通的，等撞到墙再说
- **iframe 内的 L2**——坐标换算要知道 iframe 在顶层的位置，跨源时拿不到。
  iframe 里主要是支付和验证码，而验证码本来就该走 `ask`

## 五、执行顺序

1. `find` 语义定位（content.js）—— `act` 的地基
2. `act` 循环（background.js）+ 工具定义（mcp-server.js）
3. 敏感页面识别（content.js + background.js）
4. 靶场加多步流程页 + 凭据页，补回归测试
5. 多 agent 连接级隔离（bridge.js 盖章 connId + background.js 双槽 + 双 client live 用例）
